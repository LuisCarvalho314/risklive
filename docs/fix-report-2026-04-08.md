A further issue was found in the experimental SECA newsmap pipeline. The frontend and documentation expected the timeline to progress one batch per UTC day, but the backend implementation in `/home/azureuser/opt/risklive/repo/risklive/src/services/seca_timeline.py` was only generating one batch per rolling window (`30d`, `7d`, `3d`). This was fixed in the home checkout by grouping rows by UTC day within each rolling window, writing one CSV and one SECA batch JSON per day, and then processing those batches sequentially. To support that, the Rust CLI in `/home/azureuser/opt/risklive/repo/risklive/experimental/crates/realtime-seca-cli/src/main.rs` was extended with a new `timeline-many` command that accepts multiple prebuilt batch JSON files and builds a timeline from them. The Python wrapper now calls that command and augments `timeline_manifest.json` with a `days` array so the frontend can associate each `tree_batch_*.json` with a specific date.

These SECA batching changes were only applied in the home checkout at `/home/azureuser/opt/risklive/repo/risklive`, not in the separate `/opt/risklive/repo` deployment. After starting the correct backend from the home checkout and triggering `/trigger/seca-light`, logs confirmed that SECA output was being written under `/home/azureuser/opt/risklive/repo/risklive/results/web/newsmap/...`, which aligned the experimental newsmap pipeline with the manually run frontend.
